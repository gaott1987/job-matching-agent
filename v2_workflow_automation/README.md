# V2.0: Workflow 自动化流水线

## 🎯 阶段目标
将 V1 中验证成功的“超级 Prompt”工程化。利用 Dify (本地私有化部署) 构建自动化 Workflow，解决 V1 依赖手动操作、无法固化逻辑的痛点。

## 🏗️ 架构设计

本阶段采用 **“线性工作流 + 模板渲染”** 架构，分为 4 个核心环节：

1. **感知层**：JD 解析节点（多模态 Vision 模型），将 JD 截图转化为 11 个核心字段的 JSON。
2. **认知层**：综合评估节点（强文本模型），结合 JD JSON、全量档案、意向岗位池，依据动态权重算分并生成简历建议。
3. **表达层**：模板转换节点（Template），将 JSON 渲染为人类可读的 Markdown 报告。
4. **交互层**：输出节点，直接展示最终结果。

## 🤖 模型选型策略 (Model Routing)
在节点设计中，我们刻意采用了“模型路由”策略以平衡效果与成本：
| 节点 | 选用模型 | 选型理由 |
| :--- | :--- | :--- |
| 节点1：JD解析 | 轻量级 Vision 模型 | 多模态视觉提取属于感知层任务，不需要深度逻辑推理。选用轻量级模型可大幅降低 Token 成本，且响应极快。 |
| 节点2：综合评估 | 强推理大模型 | 该节点需要处理复杂的逻辑推演（岗位画像、权重计算、简历建议）。选用顶级强推理模型，确保长文本下的算分准确性和建议深度。 |

## 💡 架构解耦说明
为了让数据在系统中高效流转，本阶段将数据结构化（JSON）与视觉呈现（Markdown）进行了**物理隔离**：
- **机器可读**：节点 2 的输出严格遵循 JSON Schema，为未来接入外部 API 或存入数据库提供标准接口。
- **人类可读**：通过 Template 节点使用 Jinja2 语法渲染，确保 UI 视觉效果与 V1 完美一致。

## 🔄 关于批量处理的架构演进 (Batch Processing)

Dify 画布原生的“批量运行”依赖 CSV 文件，但 CSV 无法直接内嵌图片文件，且将复杂的遍历逻辑堆砌在画布中会导致 Workflow 极其臃肿。

**架构决策**：我们将“核心推理逻辑”与“批量任务调度”彻底解耦。V2 阶段的 Dify 画布专注于单次、高精度的任务执行。在实际生产环境中（如处理海量 JD），无需修改当前的画布结构，只需通过编写外部 Python 脚本调用 Dify 开放的 RESTful API，即可实现批量遍历、结果自动落盘为 Markdown，甚至自动对接邮件发送。这符合微服务架构中“单一职责”与“数据面/控制面分离”的设计原则。

## 🚀 如何运行
1. 在本地 Dify 中导入 `workflow/job-matching-workflow.yml`。
2. 准备 `input_files/mock_profile.md`、`input_files/mock_job_pool.md` 及测试 JD 截图。
3. 运行并查看输出。
